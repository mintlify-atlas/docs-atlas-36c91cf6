BeautySalon connects to Supabase entirely from the browser — there is no backend server proxying requests. The Supabase client is initialised once at startup using two values read directly from Vite's environment variable system. Getting these values right is the single most common source of connection issues when self-hosting, so this page explains exactly where to find them, how Vite exposes them, and how to keep them secure.

## Required Environment Variables

<ParamField query="VITE_SUPABASE_URL" type="string" required>
  The base URL of your Supabase project. Found in **Supabase Dashboard → Project Settings → API → Project URL**. It follows the pattern `https://<project-ref>.supabase.co`.

  Example:
  ```
  VITE_SUPABASE_URL="https://urhjpytguishnlqficgr.supabase.co"
  ```
</ParamField>

<ParamField query="VITE_SUPABASE_PUBLISHABLE_KEY" type="string" required>
  The **anon / public** API key for your Supabase project. Found in **Supabase Dashboard → Project Settings → API → Project API keys → anon public**. This key is safe to ship in browser code when Row Level Security (RLS) is correctly configured — it grants only the permissions you explicitly define in your RLS policies.

  Example:
  ```
  VITE_SUPABASE_PUBLISHABLE_KEY="eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
  ```
</ParamField>

<Warning>
  **Never commit real credentials to version control.** The `.env` file in this repository contains the demo project's keys. For your own deployment, create a `.env.local` file (which Git ignores by default) and place your keys there, or inject the variables through your hosting provider's environment settings (Netlify environment variables, Vercel environment variables, GitHub Actions secrets, etc.).
</Warning>

## Setting Up Your `.env` File

Create a `.env.local` file at the project root. Vite automatically loads it during `npm run dev` and `npm run build`, and it takes precedence over `.env`.

```env .env.local
VITE_SUPABASE_URL="https://<your-project-ref>.supabase.co"
VITE_SUPABASE_PUBLISHABLE_KEY="<your-anon-public-key>"
```

<Note>
  The `VITE_` prefix is **mandatory**. Vite intentionally strips all environment variables that do not start with `VITE_` from the client bundle to prevent accidental exposure of server-side secrets (database passwords, service-role keys, API tokens, etc.). Any variable without the prefix will be `undefined` in the browser and will cause the Supabase client to fail silently.
</Note>

## How the Supabase Client is Initialised

The Supabase client is created once in `src/integrations/supabase/client.ts` and exported as a singleton. Every component and hook in the app imports from this file rather than creating its own client instance.

```typescript src/integrations/supabase/client.ts
// This file is automatically generated. Do not edit it directly.
import { createClient } from '@supabase/supabase-js';
import type { Database } from './types';

const SUPABASE_URL = import.meta.env.VITE_SUPABASE_URL;
const SUPABASE_PUBLISHABLE_KEY = import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY;

// Import the supabase client like this:
// import { supabase } from "@/integrations/supabase/client";

export const supabase = createClient<Database>(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, {
  auth: {
    storage: localStorage,
    persistSession: true,
    autoRefreshToken: true,
  }
});
```

A few things to note about this configuration:

- **`storage: localStorage`** — Auth session tokens are persisted in the browser's `localStorage`. This means users remain logged in across page refreshes and browser restarts until their token expires or they explicitly sign out.
- **`persistSession: true`** — The session is written to storage on every auth state change.
- **`autoRefreshToken: true`** — The client will silently refresh the JWT before it expires, keeping long-running admin sessions alive without requiring a re-login.
- **Typed client** — The generic `createClient<Database>` call wires in the full TypeScript types generated from your Supabase schema (defined in `src/integrations/supabase/types.ts`), giving you end-to-end type safety on all queries.

To use the client anywhere in the codebase:

```typescript
import { supabase } from "@/integrations/supabase/client";

const { data, error } = await supabase
  .from("appointments")
  .select("*")
  .eq("status", "pending");
```

## Security Considerations

<Accordion title="Is it safe to expose the anon key in client-side code?">
  Yes — with one important caveat. The Supabase **anon key** is designed to be public. It identifies your project but does not grant blanket access to your data. What controls access is **Row Level Security (RLS)**, which is enabled on every table in BeautySalon's schema.

  For example, the `appointments` table allows anonymous users to `INSERT` (so clients can book without an account) but only authenticated users can `UPDATE` or `DELETE`. The `staff`, `services`, and `staff_categories` tables allow public `SELECT` but restrict writes to authenticated users. These policies are enforced on the Postgres server — no client-side code can bypass them.

  The key you must **never** expose is the **service-role key**. That key bypasses RLS entirely and should only be used in server-side code or the Supabase dashboard.
</Accordion>

<Accordion title="What happens if VITE_SUPABASE_URL is missing or wrong?">
  If either environment variable is `undefined` at build time, `createClient` will receive `undefined` as its first or second argument. You will see a runtime error like `Invalid URL` or requests will silently fail with network errors. Check the browser console for `TypeError: Failed to construct 'URL'` — that is the most common symptom of a missing `VITE_SUPABASE_URL`.
</Accordion>

<Accordion title="How do I set environment variables on Netlify or Vercel?">
  Both platforms let you configure environment variables through their dashboards — no `.env` file is needed in production.

  **Netlify:** Go to **Site settings → Environment variables → Add variable**.

  **Vercel:** Go to **Project Settings → Environment Variables → Add New**.

  Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` with your project's values. The next deployment will pick them up automatically.
</Accordion>

## Local Development with the Supabase CLI

If you want to run a fully local Supabase stack (Postgres + Auth + Storage running in Docker) rather than using a cloud project, the Supabase CLI supports this out of the box.

```bash
# Install the Supabase CLI
npm install -g supabase

# Start the local Supabase stack (requires Docker)
supabase start
```

After `supabase start` completes it will print a local API URL and anon key. Update your `.env.local` to point at the local stack:

```env .env.local
VITE_SUPABASE_URL="http://localhost:54321"
VITE_SUPABASE_PUBLISHABLE_KEY="<local-anon-key-from-supabase-start-output>"
```

<Tip>
  The local Supabase project ID is `urhjpytguishnlqficgr` (as set in `supabase/config.toml`). When running locally, the CLI uses this ID to namespace its Docker containers, so you can run multiple local projects side by side without conflict.
</Tip>
